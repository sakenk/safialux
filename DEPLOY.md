# Деплой SanLux: база, окружение, безопасность

Пошаговый раннбук: от пустого Supabase-проекта до сайта на sanlux.kz с админкой,
заказами и уведомлениями. Каждый шаг — то, что делаете руками вы; код уже готов.

## 1. Создать базу данных (Supabase)

Supabase — это Postgres-база + автоматическое REST/RLS поверх неё. Бесплатного
тарифа достаточно для старта.

1. Зайти на supabase.com → Sign up (можно через GitHub) → **New Project**.
2. Organization — создать, если это первый проект.
3. Name: `sanlux` (любое, не влияет на код).
4. Database Password — сгенерировать, **сохранить отдельно** (в приложении не
   используется, нужен только для прямого psql-доступа, если он понадобится).
5. Region — ближайшего к Казахстану региона у Supabase нет; берите Frankfurt
   (`eu-central-1`) или Singapore (`ap-southeast-1`) — разница в задержке для
   магазина такого размера не заметна.
6. Pricing Plan — Free для старта. **Важно:** бесплатный проект Supabase
   приостанавливается после 7 дней без запросов — раз в неделю понадобится
   зайти и нажать «Restore», либо сразу перейти на Pro ($25/мес), когда сайт
   станет боевым — там же появляются нормальные бэкапы.
7. Подождать ~2 минуты, пока проект поднимется.
8. **Settings → API** — здесь три значения, которые пойдут в переменные
   окружения (см. раздел 4):
   - `Project URL` → `NEXT_PUBLIC_SUPABASE_URL`
   - `anon` `public` key → `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
   - `service_role` key (кнопка «Reveal») → `SUPABASE_SERVICE_ROLE_KEY` —
     **это ключ с полным доступом ко всей базе в обход всех ограничений,
     никому не показывать и нигде кроме .env.local / Vercel не вставлять.**

## 2. Применить миграцию (создать таблицы)

Файл `supabase/migrations/0001_init.sql` в репозитории — единственный источник
схемы. Применяется вручную через SQL Editor:

1. В панели Supabase слева — **SQL Editor → New query**.
2. Открыть `supabase/migrations/0001_init.sql` у себя в редакторе, скопировать
   файл целиком.
3. Вставить в SQL Editor → **Run**.
4. Должно отработать без ошибок и создать 5 таблиц, индексы, RLS-политики и
   стартовые данные: 5 категорий и 12 брендов (товаров, заказов и заявок пока
   нет — это нормально, товары добавляются потом через `/admin/products`).
5. Проверить: **Table Editor** слева → таблица `categories` — 5 строк, `brands`
   — 12 строк.

Файл написан безопасно для повторного запуска (`create table if not exists`,
`drop policy if exists` + `create policy`, `on conflict (slug) do nothing`) —
если не уверены, применилось ли всё, можно выполнить его ещё раз, это ничего
не сломает и не задвоит данные.

Если у проекта в будущем появятся новые поля — миграция для них будет новым
файлом `supabase/migrations/0002_*.sql`, применяется так же через SQL Editor.

### Какие таблицы создаёт миграция

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `categories` | Разделы каталога (Ванны, Раковины, Унитазы...) | `slug`, `name`, `image_url`, SEO-поля (`h1`, `seo_title`, `seo_description`, `seo_text`), `is_published` |
| `brands` | Производители (Grohe, Cersanit...) | те же SEO-поля + `logo_url`, `country` |
| `products` | Товары | `category_id`/`brand_id` (внешние ключи), `price`, `old_price`, `wholesale_prices` (jsonb — оптовые ступени `[{min_qty, price}]`), `images` (jsonb-массив фото), `specs` (jsonb-характеристики), флаги `is_featured`/`is_new`/`is_sale`/`in_stock`/`is_published` |
| `orders` | Заказы с сайта | `number` (человекочитаемый номер, автоинкремент с 1001), контакты покупателя, `items` (jsonb-снимок состава на момент заказа — не ссылка на товары, чтобы старый заказ не менялся при правке цены), `total`, `status` |
| `leads` | Заявки (подбор, запрос КП, вопрос) | `name`, `phone`, `message`, `source`, `product_id`, `status` |

`products` дополнительно получает индекс полнотекстового поиска (`to_tsvector`
по названию и артикулу) и триггер, который сам обновляет `updated_at` при
любом изменении строки.

## 3. Хранилище фото (Cloudinary)

1. cloudinary.com → бесплатная регистрация.
2. На главной странице дашборда сразу видны **Cloud name**, **API Key**,
   **API Secret** — копировать как есть, дополнительных настроек не нужно.
3. Папки `sanlux/products`, `sanlux/categories`, `sanlux/brands` создаются
   автоматически при первой загрузке фото из админки — руками ничего не
   заводить.

## 4. Переменные окружения — что это и где лежит

**Локально** (у вас на компьютере, для `npm run dev`) — файл `.env.local` в
корне проекта. Его не существует по умолчанию: скопируйте `.env.local.example`
и впишите значения:

```bash
cp .env.local.example .env.local
```

`.env.local` **никогда не попадает в git** — это прописано в `.gitignore`
(`.env*` исключён, в репозитории лежит только `.env.local.example` — пустой
шаблон без секретов). Проверяйте `git status` перед коммитом, если вдруг
редактировали `.gitignore`.

**В проде** (на Vercel, см. раздел 6) — те же переменные вписываются в
**Project → Settings → Environment Variables**, по одной, без файла. Vercel
подставляет их в момент сборки и запроса, наружу (в браузер) не отдаёт —
кроме тех, что специально помечены префиксом `NEXT_PUBLIC_`.

### Полный список переменных

| Переменная | Куда попадает | Секрет? | За что отвечает |
|---|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | и сервер, и браузер | нет | адрес проекта Supabase |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | и сервер, и браузер | нет* | публичный ключ, доступ ограничен RLS (раздел 7) |
| `SUPABASE_SERVICE_ROLE_KEY` | только сервер | **да** | полный доступ к базе в обход RLS — только в API-роутах админки |
| `NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME` | и сервер, и браузер | нет | для построения ссылок на изображения |
| `CLOUDINARY_CLOUD_NAME` / `CLOUDINARY_API_KEY` / `CLOUDINARY_API_SECRET` | только сервер | **да** | загрузка фото из `/admin` |
| `ADMIN_PASSWORD` | только сервер | **да** | пароль входа в `/admin` |
| `ADMIN_SESSION_SECRET` | только сервер | **да** | ключ подписи cookie-сессии админа (раздел 7) |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` | только сервер | **да** | уведомление о заказе в Telegram |
| `NEXT_PUBLIC_SITE_URL` | и сервер, и браузер | нет | canonical-ссылки, sitemap, Open Graph |
| `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION` / `NEXT_PUBLIC_YANDEX_VERIFICATION` | и сервер, и браузер | нет | код подтверждения сайта в поисковиках |

\* публичный ключ Supabase рассчитан на то, чтобы быть виден в браузере — он не
даёт доступа ни к чему, что не разрешено RLS-политикой в базе.

`ADMIN_SESSION_SECRET` — не пароль, а отдельная длинная случайная строка.
Сгенерировать:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

## 5. Как это подключается друг к другу (коротко о коде)

- `src/lib/supabase.ts` — читает `NEXT_PUBLIC_SUPABASE_*` для обычных запросов
  каталога и `SUPABASE_SERVICE_ROLE_KEY` для админки; если ключей нет —
  `isSupabaseConfigured`/`isAdminDbConfigured` возвращают `false`, и сайт сам
  переключается в демо-режим (текущее состояние прямо сейчас).
- `src/app/api/admin/upload/route.ts` — читает `CLOUDINARY_*` при загрузке фото.
- `src/lib/admin-auth.ts` — читает `ADMIN_PASSWORD` (сверка пароля) и
  `ADMIN_SESSION_SECRET` (подпись cookie).
- `src/lib/telegram.ts` — читает `TELEGRAM_*`; без них просто ничего не
  отправляет, заказ всё равно сохраняется.
- `src/lib/seo.ts` / `src/app/sitemap.ts` — читают `NEXT_PUBLIC_SITE_URL`.

Ничего руками «соединять» не нужно — как только переменная окружения задана,
соответствующая часть сайта сама начинает её использовать при следующем
запросе (локально после перезапуска `npm run dev`, в проде — после деплоя).

## 6. Деплой (Vercel)

Код уже на GitHub: `github.com/sakenk/safialux`, ветка `main`.

1. vercel.com → **Add New → Project → Import Git Repository** → выбрать
   `sakenk/safialux`.
2. Framework Preset определится сам (Next.js).
3. **Environment Variables** — вставить все переменные из таблицы раздела 4,
   Environment: Production (и, если хотите тестовое окружение на отдельной
   ветке — отдельно для Preview, со своим тестовым проектом Supabase, как
   сделано у vauva в `ENVIRONMENTS.md`; для старта не обязательно).
4. **Deploy**.
5. Домен: **Settings → Domains → Add** → `sanlux.kz` → на регистраторе домена
   прописать A/CNAME записи, которые покажет Vercel → SSL-сертификат
   выпустится автоматически, обычно за несколько минут.
6. На старом сайте (`sanluxkz.tilda.ws`, панель Tilda) настроить 301-редирект
   на `sanlux.kz` — иначе позиции в поиске со старого сайта не перейдут на
   новый (это отдельно от редиректов `next.config.ts`, те работают только
   внутри самого нового сайта).

## 7. Безопасность

- **RLS (Row Level Security) в Postgres.** Включён на всех 5 таблицах.
  У `categories`/`brands`/`products` есть ровно одна политика — `select` для
  строк с `is_published = true`: анонимный ключ может только читать
  опубликованный каталог, ничего не может писать. У `orders`/`leads` политик
  **нет вообще** — с публичным ключом их не прочитать и не записать никак;
  единственный способ попасть в эти таблицы — через API-роуты сайта
  (`/api/orders`, `/api/leads`, `/api/admin/*`), которые используют
  `service_role`-ключ на сервере.
- **`service_role`-ключ никогда не уходит в браузер.** Файлы, где он
  используется, начинаются с `import "server-only"` — это принудительно
  ломает сборку, если такой код случайно попадёт в клиентский компонент.
- **Сессия админа — не пароль в cookie.** В cookie лежит `срок.подпись`, где
  подпись — HMAC-SHA256 от срока действия на ключе `ADMIN_SESSION_SECRET`
  (`src/lib/admin-auth.ts`). Даже украв cookie, без секрета её не подделать и
  не продлить; сверка — по времени константным сравнением (`safeEqual`),
  чтобы нельзя было подобрать пароль по разнице во времени ответа. Cookie
  `httpOnly` (не видна JS), `secure` — только в проде (по HTTPS), срок — 14
  дней.
- **`/admin/*` и `/api/admin/*` перехватываются `src/proxy.ts`** до того, как
  выполнится код страницы — без валидной сессии сразу редирект/401. Каждая
  страница и API-роут админки дополнительно проверяют сессию ещё раз сами
  (`requireAdminPage`/`adminApiGuard`).
- **Защита форм от ботов** (`/api/orders`, `/api/leads`, `/api/admin/login`):
  honeypot-поле (скрытое поле, которое не должен заполнять человек) + форма
  не принимается, если отправлена быстрее чем за 3 секунды после загрузки, +
  лимит попыток по IP в памяти процесса (`src/lib/rate-limit.ts`). Этот лимит
  — на уровне одного серверного процесса, а не общий на весь Vercel: это
  вторичная защита, основная — honeypot и минимальное время заполнения. Если
  спам-заказы станут проблемой — следующий шаг эскалации: добавить Cloudflare
  Turnstile (капча без картинок) на формы, это не сделано сейчас, чтобы не
  усложнять первый запуск.
- **Секреты не в git.** `.gitignore` исключает `.env*` целиком, кроме
  `.env.local.example` (шаблон без значений). Если ключ всё же утёк — его
  можно перевыпустить в панели Supabase/Cloudinary/Telegram и обновить в
  Vercel; старый ключ сразу перестаёт работать.
- **HTTPS** — автоматически на Vercel (сертификат Let's Encrypt), продлевается
  сам.
- **Бэкапы базы.** На бесплатном тарифе Supabase у автоматических бэкапов
  небольшой срок хранения и нет point-in-time restore. Когда пойдут реальные
  заказы — либо перейти на Pro-тариф (ежедневные бэкапы с хранением), либо
  время от времени выгружать данные вручную: Table Editor → таблица → Export
  as CSV, или `pg_dump` по строке подключения из Settings → Database.

## 8. После первого деплоя — чек-лист

1. Зайти на `sanlux.kz/admin`, войти по `ADMIN_PASSWORD`.
2. Добавить настоящие товары с фото через `/admin/products` (демо-товары
   показывались только пока Supabase не был подключён).
3. Дописать `seo_text` для «Смесители» и «Инсталляции» через
   `/admin/categories` — сейчас это поле пустое.
4. Оформить один тестовый заказ на живом сайте: проверить, что он появился в
   `/admin/orders`, пришло уведомление в Telegram и открылся WhatsApp с
   текстом заказа.
5. Google Search Console и Яндекс.Вебмастер — подтвердить домен (коды из
   раздела 4), отправить `sitemap.xml`.
6. Завести/обновить профиль в 2ГИС и Google Business с тем же адресом и
   телефоном, что на сайте.
